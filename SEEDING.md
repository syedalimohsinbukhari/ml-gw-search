# Seeding scheme for the regenerated dataset (ml-gw-search)

Written 2026-10-19T20:55Z in `ml_practice_v2`, revised 2026-10-19T21:45Z for the shard design, and moved here on 2026-10-19T22:06Z when each repository got its own master seed.
Status: design agreed with the user; no code implements it yet.
This repository's master seed is separate from the one in `ml_practice_v2` (which seeds training and tests there); the two values are unrelated, and neither repository reads the other's.
Rules come from `ml_practice_v2/CLAUDE.md` §14 (determinism) and §6 of `ml_practice_v2/WORKING_CONVENTIONS.md` (a generated file carries its provenance).
The dataset layout, the frozen generator backend, and the decisions behind this scheme are in `ml_practice_v2/GENERATOR_OVERHAUL.md`.
The scheme was adapted from a `SEEDING.md` that came from another repository (a GRB paper codebase).

## Why

The generator (`mlgwsc-1/gen.py`) is unseeded, and the dataset in use, `combined_repackaged.hdf`, cannot be regenerated bit-for-bit.
Two causes are verified by code read:

- `np_gen = np.random.default_rng()` has no seed and no CLI option.
- pycbc's noise draw (`frequency_noise_from_psd`) and sky-location draw (`UniformSky.rvs`) use the legacy global `numpy.random`, so seeding `np_gen` alone leaves them random.

A seed literal also sits in `re_package_hdf.py` (`132354`).
The generator backend (`gen.py`, `whiten`, `regularize_psd`) is part of a published paper and is not edited; the scheme is applied by a driver that wraps it.

Drawn on host `thinkpad-t530` from the OS CSPRNG, not from NumPy, so it depends on no generator state.

## The shard design

The dataset is 13 shards of 10,000 samples, each 5,000 injections followed by 5,000 noise-only samples, and each generated by its own process.

| Split | Shards | Samples per shard | Shard numbers |
|-------|--------|-------------------|---------------|
| training | 10 | 10,000 | 0 to 9 |
| validation | 2 | 10,000 | 0 to 1 |
| test | 1 | 10,000 | 0 |

The shard number counts within a split, so adding training shards later never touches the validation or test shards.
A shard file holds one split.

## Derivation: one key per dataset, split, shard, and purpose

Every seed is a `numpy.random.SeedSequence` keyed by `MASTER_SEED` and an explicit integer tuple.
The tuple is the key, so a seed never depends on call order, process order, machine, or checkout path.

```python
def seed_seq(dataset_id: int, split: int, shard: int, purpose: int) -> np.random.SeedSequence:
    return np.random.SeedSequence(MASTER_SEED, spawn_key=(dataset_id, split, shard, purpose))
```

| Level | Values | Meaning |
|-------|--------|---------|
| `dataset_id` | 0 for this regeneration | anything that changes the generating distribution gets a new id, so a later dataset never reuses these draws; reuse an id only to pair datasets on purpose |
| `split` | 0 = training, 1 = validation, 2 = test | separate streams per split |
| `shard` | 0, 1, 2, … within the split | one output file and one process |
| `purpose` | 0 = injection `rng`, 1 = pycbc global state, 2 = SNR draw | independent draws that must not share a stream |

Checked on 2026-10-19T21:43Z (numpy 2.2.6, with the master above):

- The 39 keys (13 shards × 3 purposes) give 39 distinct states, and every key differs between `dataset_id` 0 and 1.
- Keys already in use are unchanged when further shards are added, and the same shard number in another split differs.
- A rebuilt key reproduces its draws, and `numpy.random.seed` with the four-word state reproduces its normal draws and differs for another shard.
- The control reads correctly: seeding with the same literal twice gives identical streams, which is the failure the scheme avoids.

## Usage pattern (decided: option A for pycbc)

Each shard process does, once, at its start:

```python
rng = np.random.default_rng(seed_seq(dataset_id, split, shard, 0))       # injection parameters
np.random.seed(seed_seq(dataset_id, split, shard, 1).generate_state(4))  # pycbc noise and sky draws
gen.np_gen = rng                                                         # the generator reads this module global
```

and then calls `generate_dataset` once for the shard, with the unchanged backend, so one `rng` is threaded through every injection draw.

- Never pass `seed=` to a pycbc call inside the sample loop.
  The same seed per call gives identical noise on every call, and also identical H1 and L1 noise within a sample (verified: the same seed reproduces the same noise).
- The global `numpy.random.seed` call is made once per shard process, with a state distinct from every other shard, which is why it does not recreate the reseed-per-iteration bug.
  It is the one place that deviates from "thread one generator", because pycbc cannot be handed a generator.
- The noise of every sample, injection or noise-only, comes from the pycbc global state, and the injection draws come from `rng`, so a shard's output depends only on its key and on its own counts.
  Changing a shard's counts changes that shard only; the other shards stay identical.
- The SNR draw belongs to the repackaging step, which runs per shard with `purpose = 2`, so a shard's SNRs do not depend on any other shard or on the merge order.
- Rejected: drawing a 32-bit seed per call from the `rng` (about 24–34% chance per file that two noise calls share a seed).
- Not chosen now: spawning a per-call seed array from the `rng` (option B), and rewriting the noise and sky draws to use `np_gen` (option C, the purest design, to be revisited if the global-state deviation proves a problem).
  Both would edit or wrap the backend more deeply, which the freeze rules out for now.

## What each generated file records

A generated file must be checkable without its generating script, so these go in the HDF attributes (and not only in a registry):

- `master_seed`, `dataset_id`, `split`, `shard`, and the keys used for the three purposes.
- The number of injections and of noise-only samples in the shard.
- The `gen.py` arguments (approximant, noise source, detector count, sample length, sample counts).
- The git SHA of this repository, the hashes of the frozen backend (`gen.py`, `whiten`, `regularize_psd`), and the python, numpy, pycbc, and h5py versions.
- The UTC time of generation, and the host.
- The column names of `params`, matching what the file actually contains.
- In the merged file: the list of shards with their keys, the merge order (fixed, by split and shard number), and a final `complete` attribute.

Any seed registry or table for the paper is generated by a script from these attributes, never hand-assembled.

## Determinism check (run 2026-10-22T07:26Z on a shrunken workload: all six steps passed, see `HANDOFF.md`)

Before any full generation, on a shrunken workload (for example 3 injections and 3 noise-only samples per shard) that is reverted afterwards, and only with the user's go-ahead on a machine other than `thinkpad-t530`:

1. Generate one shard twice from the same key; compare `noises`, `waveforms`, and `waveform_params` for exact equality.
2. Generate a different shard number, and the same shard number in another split; the arrays must differ.
3. In one process generate shard A, then shard B, then shard A again; the two copies of A must be identical, which shows no state leaks between shards.
4. Check that H1 and L1 noise within a sample differ.
5. Run the repackaging step twice on one shard; the baked SNRs must be identical, lie in the configured range, and differ for another shard.
6. Merge the shards in two different input orders; the merged files must be identical, because the merge sorts by split and shard.

Falsified by: any difference in steps 1, 3, 5 or 6, any equality in step 2 or 4.
Compare arrays, not file bytes, since whether h5py writes byte-identical files is unknown.
Differences only at float-rounding level (for example from FFT threading) are a decision point for the user, not something to resolve quietly.
This repository has no test suite, so this is covered only by an ad-hoc check unless a test is added.
